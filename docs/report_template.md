# 最终报告：固定周预算下 coding agent 的维护与实现分配

看板：[docs/index.html](docs/index.html)（英文版 [docs/index.en.html](docs/index.en.html)；GitHub Pages 开启后为 https://changkun.github.io/agent-budget/ ）。原始日志在 `docs/data/`。计划与规则见 [PLAN.md](PLAN.md)。从前提、理论模型到证据的完整推导见方法论页面 [docs/methodology.html](docs/methodology.html)。后续实验（维护的必要性是否随模型能力变化）见 [REPORT-capability.md](REPORT-capability.md)。

## 结论摘要

- **真实运行（claude-sonnet-5-5，每组 3 次重复）：前提不成立（限于本实验条件）。**
  - 维护组 8 周累计完成 23–24 项，不维护组 29–31 项，三次重复的范围不重叠。
  - 不维护组的每项成本确实上升了：后期/前期比 1.12–1.21。但维护组也在上升：1.08–1.11。
  - 同一个 backlog 项在两组里的成本几乎一样：维护组 ÷ 不维护组平均为 1.03，单项在 0.93–1.18 之间。这说明成本上升主要来自排在后面的 backlog 项本身更大，而不是代码库变差。
  - 维护确实让指标留在基线附近：期末覆盖率 92–97%，不维护组为 68–70%；最大文件 88–104 行，不维护组为 144–182 行。但在 8 周、约 30 项、代码从约 660 行长到约 1300 行的规模内，这些变差没有带来可见的成本上升或验收失败。173 个正式会话没有一次验收失败，调试一次也没触发。
  - 维护花掉 23% 的预算，直接换成了少交付约 7 项。
- **模拟：结论随假设改变。** “技术债影响强”下，不维护组每项成本后期约为前期的 1.4–2.6 倍，维护组持平，但 8 周内维护组累计交付仍少约 2 项；“技术债影响弱”下维护组少交付约 7 项。模拟结果不能用来判断前提是否成立。
- **花费：** 第二阶段合计 13.07 美元，上限 600 美元，明细如下：

  | 项目 | 美元 |
  |---|---|
  | 可行性探测 | 0.08 |
  | 校准 | 0.42 |
  | 6 个有效系列 | 10.80 |
  | 作废并重跑的 maint-r2 首次运行 | 1.78 |
- 以上都是描述，不声称统计显著。

## 1. 实验设置

- 两组：不维护组（全部预算用于实现和调试）与维护组（每周开始测量指标，越过阈值就运行对应的维护 agent，剩余预算用于实现）。
- 8 周，每周一份固定预算，用不完作废；周超支从下一周扣除。backlog 40 项，固定顺序，两组相同。
- 每周预算 = 校准单项平均成本 × 4.5；单项上限 = 校准成本 80 分位数 × 1.5。剩余预算小于单项上限时本周结束。会话跑完为止，超过上限的部分记为超支，之后不再开调试会话。验收失败后最多调试 2 次，仍失败则回滚、记为失败。
- 指标以第 0 周为基线，阈值见 `config/thresholds.toml`：漏洞数 > 0；覆盖率相对下降 > 5%；重复代码比例相对上升 > 30%（基线不足 2% 时按 2% 计）或最大文件行数相对上升 > 50%；实现任务平均输入 token 相对上升 > 20%。
- 每项成本 = 一段时间内（实现 + 调试）花费 ÷ 完成项数，维护花费不计入。
- 价格：claude-sonnet-5-5 官方价（输入 2，1 小时缓存写入 4，缓存命中 0.10，输出 10，单位美元/百万 token），日志里的成本都按这张表自算。

## 2. 模拟结果

**模拟结果只反映所设的假设系数，不能用来判断前提是否成立。** 两组假设的代码库变差速度相同，只在“变差对成本和失败率的影响”上不同；随机数对两组、两种假设相同（公共随机数）。系数见 `config/sim/`。

结论如何随假设变化（3 次重复，描述性，不作显著性判断）：

| | 不维护组累计完成 | 维护组累计完成 | 不维护组后期/前期成本比 | 维护组后期/前期成本比 | 维护花费占比 |
|---|---|---|---|---|---|
| 技术债影响强 | 13–18（均值 16.0） | 12–15（均值 13.7） | 1.39–2.63（均值 1.90） | 0.72–1.02（均值 0.86） | 29.7% |
| 技术债影响弱 | 16–24（均值 20.3） | 12–15（均值 13.7） | 1.03–1.27（均值 1.13） | 0.64–1.30（均值 1.00） | 40.5% |

- “强”假设下，不维护组的每项成本逐周上升（后期约为前期的 1.4–2.6 倍），维护组基本持平。但维护组约 30% 的预算花在维护上，8 周内省下的实现成本不足以抵消，累计交付仍少约 2 项。“弱”假设下维护没有收益，维护组少交付约 7 项。也就是说，在这组系数下，假设越强，两组差距越小，但 8 周内没有翻转。
- 差距主要来自维护本身的成本：按设定，一次维护约等于 1–2 项实现的花费，而阈值以第 0 周为基线、平均输入 token 由每周约 3 个会话平均得到，噪声就足以触发知识提炼。在“弱”假设下，维护组 3 次重复合计运行了 19 次维护。
- “强”假设的不维护组里，几乎所有指标都和每项成本正相关，包括模型里对成本没有任何作用的过期依赖数（Pearson 0.46）。这说明在这种设计下，相关性主要反映指标和成本共同随时间上升，不能当作因果证据。
- 周初预计平均比周末实际多约 1 项。原因是预计公式没有考虑“剩余不足一个上限就停止”的规则，每周约 1/3 预算按规则作废。

## 3. 真实运行结果

单项平均成本远低于原计划的设想：校准均值 0.071 美元，正式运行中每项 0.04–0.09 美元。所以每周预算只有 0.318 美元，单项上限 0.127 美元。按每组 3 次重复描述：

1. **交付量。** 不维护组每周约 3.3–5 项，8 周累计 29–31 项，40 项 backlog 没有做完。维护组在触发维护的周（主要是第 3、7、8 周）只完成 1–2 项，累计 23–24 项。
2. **每项成本随周数变化。** 两组都在第 2 周后从约 0.05 美元升到约 0.06 美元，之后在 0.055–0.075 美元之间波动。
   - 不维护组后期/前期比 1.12–1.21，维护组 1.08–1.11。
   - 两组的上升幅度接近。backlog 项编号与该项成本的相关系数为 0.31（不维护组）和 0.25（维护组）：两组按同一顺序做同样的项，后面的项更大。
   - 按项配对比较时，维护组并不更便宜。
3. **平均输入 token。** 每次实现会话 7–10 万 token，没有随代码变大而上升。它一直低于第 0 周基线：基线 10.3 万来自校准任务，校准任务本身偏大。
   - 知识提炼从未触发，`CLAUDE.md` 从未生成。
   - 漏洞数和过期依赖数始终为 0，安全维护也从未触发。
4. **维护。** 3 次重复合计 12 次维护任务：补测试 7 次、代码整理 5 次，全部通过构建和测试检查，没有回滚。
   - 每次花费 0.07–0.19 美元，约等于 1.2–3 项实现。
   - 有 3 次超过了单项上限，记为单项超支；没有周超支。
5. **验收与调试。** 两组所有实现会话都是第一次就通过验收，平均调试次数为 0。按设计，技术债可能通过“失败率上升”增加成本，这条路径在本实验中没有出现。
6. **指标与每项成本的相关性**（周初指标对当周每项成本，合并 3 次重复，每组 23–24 个周样本）：
   - 代码行数 0.41 / 0.39，覆盖率 −0.50 / −0.29，最大文件行数 0.35 / 0.52（前为不维护组，后为维护组）。
   - 这些指标都随时间单调变化，后面的周又做更大的项，所以相关性不能当作因果证据。
   - 平均输入 token 呈负相关（−0.52 / −0.27）。它是上周的平均值，主要反映周与周之间的随机波动。
   - 表中“–”表示该指标在所有周初都没有变化（重复比例、漏洞数、过期依赖数），无法计算相关性。
7. **预测误差。** 周初预计平均比周末实际多 1.7–1.9 项。原因有二：预计公式没有考虑“剩余不足一个上限就结束本周”，这条规则每周让约 30% 的预算作废；第 1 周用的校准均值也高于实际单项成本。

**结论：前提不成立（限于本实验条件）。** 在这个规模和期限内，不维护并没有让单项实现成本明显变贵或更容易失败；而按阈值触发的维护花掉约四分之一预算，直接减少了交付。这个结论不能外推到大得多的代码库、更长的期限或更弱的模型。

**数据更正。** maint 组第 2 次重复第一次运行时，有一个会话启动了后台任务，CLI 因此输出了两个 result 事件，旧的解析器只计了最后一轮的用量。日志记成 0.008 美元，实际是 0.172 美元，导致该系列从第 3 周起的调度不符合规则。解析器修正后：

- 182 个会话的成本全部与 CLI 的累计值核对一致；
- 该系列用相同配置从头重跑，原日志存档在 `docs/data/real/invalid/` 并附说明，不进入看板和统计；
- 其他系列没有受影响。

## 4. 局限

- **规模小。** 网站从约 660 行长到约 1300 行，backlog 项彼此独立，验收测试对 agent 可见。这种条件下模型几乎不会失败，技术债通过失败率起作用的路径没有被检验到。
- **期限短。** 8 周约 30 项。维护的收益如果要更长时间才显现，本实验看不到。
- **阈值以第 0 周为基线。** 平均输入 token 的基线来自 6 个校准任务，而校准任务比前几项 backlog 大，所以知识提炼从未触发。原始网站重复比例为 0，加了 2% 的基线下限（运行前确定，见 PLAN.md 第 8 节）。
- **混杂因素。** 每项成本按周比较时，与 backlog 项本身的大小混在一起，所以报告补充了按项配对的比较。
- **样本量。** 每组只有 3 次重复，结论只作描述。
- **价格与缓存。** 成本按 2026-10-07 的官方价格表自算。缓存命中价当天从 0.20 降到 0.10 美元/百万 token，CLI 自报的成本仍按 0.20 计，两列都在日志里。并行会话之间可能共享提示缓存，这对两组的影响相同。
- **隔离。** agent 在 bypassPermissions 模式下理论上能读到工作副本之外的文件；提示中要求只在当前目录工作。
- **标签。** 云端环境不允许推送 git 标签，起点只存在于本地标签 `site-v0`。对应提交 4a0ea0c 已推送，记录在 run.json 里。
- **模拟系数。** 模拟按每个会话约 60 万输入 token 设定，真实会话只有 7–13 万 token，两者不能直接对照。
